# 备份与恢复

设置页“导出 JSON”在已登录且有权读取时生成版本 1 内容备份，包含 records、site settings 和 media metadata。文件由用户主动下载，不放到 `public/`，也不自动上传外部服务。导出范围须明确；纪念册只包含用户主动选择的条目。

**JSON 的 `mediaFilesIncluded:false` 表示不包含图片、音乐、视频的 bytes。** JSON 能恢复文本及关系，不能重新生成已经丢失的媒体文件。

本地完整备份：停止应用 → 复制整个 `STARS_DATA_DIR`（默认 `.data`，包含 SQLite 以及 `media/`）到受保护位置 → 保存一个独立 JSON 导出 → 记录创建时间、应用版本及数据目录 → 在另一个目录检查复制的文件。SQLite 使用 WAL，应用运行中仅复制主 `.sqlite` 文件可能缺少已提交内容；应用停机后复制整个目录最简单可靠。不把备份放进公开仓库或公共静态目录。

云端完整备份：使用 Supabase 当前支持的数据库备份/CLI 导出，并单独导出私有 Storage 对象；数据库备份通常不含 Storage 文件。必须保留路径和媒体 ID。Auth 用户与 profiles allowlist 也是恢复环境的授权组成，不能只复制三张内容表就认为账户迁移完整。根据套餐核实保留天数与恢复费用。

恢复流程：选择 JSON → 服务端校验版本、所有字段、ID、日期和引用 → 展示将新增/更新的数量、设置变化和缺失媒体 → 阅读预览 → 二次确认恢复。恢复按 ID 合并，不清空现有记录、不静默替换全部数据库。本地使用一个 SQLite 事务，云端使用 SECURITY INVOKER 的 `restore_backup` RPC 单事务；任一失效关系、所有权错误或重复 ID 会使整次恢复失败。

当前媒体目录或云端 Bucket 里不存在的文件会出现在 `missingMedia`，实际恢复返回冲突而非虚假的成功。现有元数据还在时，先恢复真实媒体文件及其正确路径，再重新预览；若元数据也已删除，应恢复完整数据库和媒体副本，仅把 bytes 放进目录不能重新建立已删除的素材身份。原目录完整复制到新机器的本地实例时，应复制数据库与媒体并保持同一所有者身份；不要先创建新的本地账号后把旧媒体路径当作新账号的资源。

恢复前再做一次完整备份。JSON 只能恢复符合当前格式的内容；不支持执行 SQL、运行脚本或任意文件写入。发生错误时保留原文件与报错，不重复上传不明路径，不删除原数据库。确认服务未写入后从停机前完整目录副本回滚。账号密码忘记时使用受控 `npm run owner:reset`，不要用内容 JSON 修改身份授权。
